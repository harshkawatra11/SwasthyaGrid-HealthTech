Bug found and fixed: a previous agent's uncommitted change to FILLER_DELAY_S (0.7 to 1.0 s) was already in the working tree; the first probe run against it showed the filler never played on any tool turn even though the real answer took 1.6 to 1.8 s to arrive. Cause: after `_run_tool_round` finished executing the tool functions (local, near instant), the code cancelled the still pending filler task on the assumption that finishing the tools meant the answer was imminent. In practice the follow up chat completion call is a second network round trip to Sarvam and was itself the slow half (measured 1.3 to 1.5 s to first token in the same probe run). Removed that premature cancellation in `_run_tool_round` (backend/app/voice/session.py); the filler now relies only on its own timer plus the existing cancellation in `_on_audio` once real answer audio actually starts. Confirmed fixed: the second probe run played the filler on all three tool turns, before the real answer audio in each case.
Probe run 1 (before the fix): no tools final to first answer audio median 1091 ms (target <= 1800, met); tools any audio median 1794 ms (target <= 1200, missed, filler never fired); tools answer audio 1638 to 1799 ms (target one tool round <= 3200, met). Filler played: never.
Probe run 2 (after the fix, server restarted to load the change): no tools final to first answer audio median 3315.5 ms; tools first any audio median 4999 ms; tools answer audio 5572 to 8130 ms. Filler played on all three tool turns, ahead of the real answer in each. Both runs hit zero transport errors and zero retries in the server log; the large jump between the two runs is Sarvam API response time varying between calls (no retries or errors were logged, so it is not a client side regression), not a code change, since the change only removed an early cancellation and cannot make the model or TTS slower. This lane cannot control that variance; flagging it rather than re running a third probe (2 probe budget already spent).
Deviations: (1) Latency numbers in run 2 exceed the 7.1 targets; this is attributed to live Sarvam API latency on the day, not a wiring defect, since protocol framing, tool dispatch, and metrics all matched expectations and the only functional gap found (the filler) was fixed and reverified.
